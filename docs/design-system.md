AquaCore Design System

1. Purpose

This document defines the visual and interaction direction for AquaCore.

The goal is to create a professional digital experience for an established swimming and aquatic training organisation.

The design should communicate:

* Trust
* Professionalism
* Safety
* Expertise
* Education
* Confidence
* Accessibility
* Modern service

The product should feel like a serious aquatic training organisation, not a generic swimming-school template or a generic SaaS dashboard.

⸻

2. Design References

AquaCore takes product and experience inspiration from established aquatic and lifesaving organisations such as:

* American Lifeguard Association
* American Red Cross Lifeguarding
* Royal Life Saving Society UK

These references should influence:

* Information hierarchy
* Course presentation
* Training presentation
* Certification experiences
* Trust signals
* Navigation
* Professional tone
* Dashboard organisation

They are references, not templates.

Do not copy:

* Logos
* Brand identities
* Proprietary illustrations
* Proprietary photography
* Exact layouts
* Exact copy
* Exact colour systems

AquaCore must have its own visual identity.

⸻

3. Overall Design Personality

The design should feel:

Professional + Modern + Human + Trustworthy + Aquatic

It should not feel:

* Childish
* Cartoonish
* Overly corporate
* Overly futuristic
* Like a gaming interface
* Like a generic Bootstrap dashboard
* Like an AI-generated landing page
* Overly luxurious without substance

The design should communicate competence before decoration.

⸻

4. Brand Direction

The working product name is:

AquaCore

This is temporary and may change later.

The brand should be flexible enough to support a future:

* Logo
* Brand colour
* Typography system
* Photography style
* Certification identity
* Training materials

Do not build the UI around the temporary logo.

The interface should remain visually coherent if the organisation changes its name or branding later.

⸻

5. Colour Direction

The visual identity should use an aquatic-inspired palette without becoming stereotypically blue.

Primary direction

Use a strong aquatic primary colour for:

* Primary buttons
* Important links
* Active navigation
* Key interactive elements
* Important highlights

Supporting colours

Use restrained neutral tones for:

* Backgrounds
* Surfaces
* Borders
* Text
* Secondary controls

Accent colours

Accent colours may be used sparingly for:

* Success
* Warning
* Error
* Informational states
* Important highlights

Do not use many competing accent colours.

⸻

6. Colour Principles

Avoid:

* Neon gradients
* Excessive blue-on-blue interfaces
* Rainbow dashboards
* Large decorative colour blocks
* Gradient text
* Excessive glassmorphism

Colour should communicate hierarchy and meaning.

A button should look clickable.

A warning should look like a warning.

A successful payment should look successful.

The interface should remain understandable without relying entirely on colour.

⸻

7. Typography

Typography should be modern, professional, and highly readable.

Recommended direction:

* Clean sans-serif typeface
* Strong heading hierarchy
* Comfortable body text
* Clear labels
* Readable form controls
* Consistent numeric styling for prices and statistics

Avoid:

* Decorative fonts
* Excessive uppercase text
* Overly condensed typography
* Excessive font weights
* Large text simply for visual impact

Typography should support information, not compete with it.

⸻

8. Typography Hierarchy

Use a consistent hierarchy.

Display

Used for:

* Major homepage headlines
* Important campaign sections
* Major page introductions

H1

Used once per major page.

H2

Used for major sections.

H3

Used for subsections and cards where appropriate.

Body

Used for normal information.

Supporting text

Used for:

* Descriptions
* Metadata
* Helper text
* Secondary information

Labels

Used for:

* Forms
* Status information
* Filters
* Table metadata

Do not create arbitrary heading sizes for individual sections.

⸻

9. Layout

AquaCore should use a clear content grid.

Public pages should generally use:

* Full-width sections where appropriate
* A constrained content container
* Consistent horizontal padding
* Clear vertical rhythm

Dashboard pages should generally use:

Sidebar
   +
Main content area

The content area should have enough density to be useful without becoming cramped.

⸻

10. Spacing

Use a consistent spacing system.

Avoid manually choosing random spacing values throughout the application.

Common spacing should be reused for:

* Section padding
* Card spacing
* Form fields
* Navigation items
* Tables
* Page headers
* Dashboard widgets

Whitespace should create hierarchy rather than simply making the page look empty.

⸻

11. Border Radius

Use restrained rounding.

Cards, buttons, inputs, and panels may have modest corner rounding.

Avoid:

* Extremely rounded cards
* Pill-shaped everything
* Excessive rounded containers
* UI elements that look inflated

Rounded elements should communicate grouping or interaction.

⸻

12. Shadows

Use shadows sparingly.

Prefer:

* Subtle elevation
* Borders
* Surface contrast

Avoid:

* Heavy floating shadows
* Multiple overlapping shadows
* Excessive glow effects

The interface should remain clean and professional.

⸻

13. Photography

Photography is important to the AquaCore experience.

When real organisation photography becomes available, it should be prioritised over generic stock imagery.

Useful photography categories include:

* Swimming lessons
* Adult swimmers
* Children learning with appropriate safeguarding considerations
* Lifeguard training
* CPR/first aid training
* Pool environments
* Instructors teaching
* Group training
* Professional aquatic environments

Photography should feel:

* Authentic
* Professional
* Well-lit
* Human
* Active
* Trustworthy

Avoid obviously staged or overly artificial imagery.

⸻

14. Homepage Direction

The homepage should quickly communicate:

1. Who the organisation is
2. What it offers
3. Who the services are for
4. Why customers should trust it
5. Where training happens
6. How to get started

A typical hierarchy may be:

Hero
↓
Key Programs
↓
Why Choose Us / Trust
↓
Training & Courses
↓
Locations
↓
Certification / Safety
↓
Testimonials
↓
Final CTA
↓
Footer

This is a structural direction, not a mandatory final layout.

⸻

15. Hero Section

The hero should communicate the organisation’s value immediately.

It should contain:

* Clear headline
* Short supporting message
* Primary CTA
* Secondary CTA where useful
* Strong visual

Possible primary actions:

* Book a Lesson
* Explore Programs
* View Training
* Contact Us

Avoid overly clever marketing copy that makes the service unclear.

The visitor should understand what the organisation does within seconds.

⸻

16. Program Cards

Program cards should communicate useful information quickly.

A program card may contain:

* Program name
* Short description
* Audience
* Training type
* Duration where known
* Starting price where appropriate
* CTA

Do not invent information simply to fill a card.

If information is unavailable, omit it or use an appropriate placeholder during development.

⸻

17. Program Detail Pages

Program pages should answer:

* What is this?
* Who is it for?
* What does it involve?
* How does it work?
* Where is it available?
* How long does it take?
* What does it cost?
* What happens after booking?
* How can I book?

The CTA should remain visible and easy to find.

⸻

18. Booking Experience

The booking flow should feel straightforward.

Recommended progression:

Program
  ↓
Location
  ↓
Preferred Date & Time
  ↓
Participant Details
  ↓
Review
  ↓
Payment
  ↓
Confirmation

Use clear progress indicators where helpful.

Do not overload one page with every possible field.

Explain why information is being requested when it may not be obvious.

⸻

19. Forms

Forms should be:

* Simple
* Clearly labelled
* Predictable
* Keyboard accessible
* Easy to correct

Every important field should have a visible label.

Validation errors should appear close to the relevant field.

Avoid vague errors such as:

Invalid input.

Prefer useful explanations such as:

Please enter a valid phone number.

⸻

20. Buttons

Buttons should clearly communicate their action.

Primary buttons should be reserved for the main action.

Examples:

* Book a Lesson
* Continue
* Pay Now
* Confirm Booking
* Save Changes

Secondary actions may use:

* Outline buttons
* Text buttons
* Secondary surface buttons

Dangerous actions such as cancellation or deletion should have clear visual distinction.

⸻

21. Status Indicators

Status indicators should use:

* Text
* Appropriate colour
* Consistent visual treatment

Examples:

Pending
Confirmed
Completed
Cancelled
Rejected
Refunded

Do not rely on colour alone.

For example:

● Confirmed
● Pending
● Cancelled

should also contain readable status text.

⸻

22. Customer Dashboard

The customer dashboard should feel like a service portal rather than a traditional enterprise admin system.

Possible structure:

Welcome
↓
Upcoming Booking
↓
Quick Actions
↓
Course Progress
↓
Recent Payments
↓
Certificates

The most important current action should receive the strongest visual emphasis.

Avoid filling the dashboard with meaningless statistics.

⸻

23. Admin Dashboard

The admin dashboard should prioritise operational information.

Potential overview:

Today's Activity
↓
Pending Bookings
↓
Recent Payments
↓
Customers
↓
Programs
↓
Courses
↓
Certificates

Useful metrics may include:

* Pending bookings
* Confirmed bookings
* Recent payments
* Customer count
* Active courses

Only display metrics that help the administrator make decisions.

Do not create decorative analytics simply because dashboard cards are available.

⸻

24. Admin Navigation

The admin sidebar should group related functionality.

Example:

Overview
Bookings
Customers
Programs
Courses
Certificates
Locations
Payments
Website
Settings

Navigation labels should be straightforward.

Avoid unnecessarily clever names.

⸻

25. Tables

Tables should be used when users need to compare or manage multiple records.

Useful examples:

* Customers
* Bookings
* Payments
* Programs
* Certificates

Tables should support appropriate:

* Sorting
* Filtering
* Search
* Pagination

Only add these capabilities when the dataset or workflow actually requires them.

Mobile layouts should provide an appropriate alternative rather than forcing a huge table into a narrow screen.

⸻

26. Cards

Cards should group related information.

Good uses:

* Program summaries
* Course summaries
* Booking summaries
* Dashboard statistics
* Certificate previews

Do not put every piece of content inside a card.

Excessive cards make the interface feel fragmented.

⸻

27. Empty States

Empty states should explain what is happening and what the user can do next.

Example:

No upcoming bookings
You don't have any upcoming training sessions yet.
[Book a Lesson]

Avoid empty screens with no explanation.

⸻

28. Loading States

Important asynchronous interfaces should provide feedback.

Use:

* Skeletons
* Loading indicators
* Disabled action states
* Progress feedback

Do not allow users to wonder whether a button click worked.

Payment and booking actions require particularly clear feedback.

⸻

29. Error States

Errors should:

* Explain the problem
* Avoid technical jargon
* Tell the user what to do next where possible

For example:

We couldn't complete your booking.
Please try again. If the problem continues, contact the organisation.

Technical details belong in logs, not normal customer-facing messages.

⸻

30. Notifications

Notifications should be useful rather than constant.

Examples:

* Booking received
* Booking confirmed
* Booking rescheduled
* Payment received
* Course update
* Certificate issued

Avoid unnecessary notifications for every minor interaction.

⸻

31. Responsive Design

Design from mobile upward.

Important customer journeys must work on:

* Mobile
* Tablet
* Desktop

Priority mobile journeys:

* Homepage
* Program discovery
* Program details
* Booking
* Payment
* Login
* Registration
* Course access
* Certificate verification

Do not simply shrink the desktop layout.

Reconsider layout and interaction where necessary.

⸻

32. Accessibility

The design should support:

* Keyboard navigation
* Visible focus states
* Semantic HTML
* Accessible form labels
* Meaningful button text
* Adequate contrast
* Screen-reader-friendly structure
* Reduced-motion preferences where applicable

Accessibility should be considered during implementation rather than added as a final cleanup task.

⸻

33. Motion

Animation should support understanding.

Good uses:

* Page transitions
* Loading feedback
* Small interaction feedback
* Expanding/collapsing content

Avoid:

* Constant floating animations
* Large entrance animations on every section
* Excessive parallax
* Decorative motion that slows the page
* Animation that interferes with forms or booking

The site should still feel professional with animations disabled.

⸻

34. Icons

Use one consistent icon system.

Icons should:

* Support meaning
* Remain visually consistent
* Have appropriate sizing
* Not replace important text

Do not use random emoji as interface icons.

⸻

35. Content Tone

Public-facing copy should be:

* Clear
* Confident
* Warm
* Professional
* Human

Avoid:

* Empty corporate language
* Excessive buzzwords
* Overpromising
* Fake urgency
* Unsupported claims
* Overly dramatic marketing language

Explain services plainly.

⸻

36. Trust Signals

Trust should come from useful evidence.

Potential trust elements include:

* Instructor information
* Training experience
* Real testimonials
* Training locations
* Certification information
* Safety practices
* Clear contact information
* Transparent booking process

Only use information that the organisation can verify.

Never manufacture trust signals.

⸻

37. Dashboard Density

Public pages can use more breathing room.

Dashboards should use information efficiently.

A good admin screen should allow an administrator to understand the situation quickly without excessive scrolling.

However, density must not become clutter.

Prioritise:

Important
   ↓
Useful
   ↓
Secondary

Do not give every element equal visual weight.

⸻

38. Design Consistency Rules

Before creating a new UI pattern:

1. Check whether an existing pattern already exists.
2. Reuse it where appropriate.
3. Extend it if the difference is minor.
4. Create a new pattern only when the use case genuinely differs.

Consistency is more important than novelty.

⸻

39. Anti-Patterns

Avoid the following unless there is a strong product reason:

* Generic Bootstrap admin appearance
* Huge hero text with little information
* Excessive gradients
* Excessive glassmorphism
* Excessive rounded cards
* Neon colours
* Cartoon swimming graphics
* Emoji-heavy UI
* Decorative dashboards
* Fake statistics
* Fake testimonials
* Fake certification badges
* Excessive animations
* Long walls of text
* Tiny unreadable text
* Desktop-only workflows
* Dark UI everywhere

⸻

40. Design Implementation Rule

Do not attempt to build the entire design system before it is needed.

Establish the foundational tokens and reusable components first.

Then evolve the design system as real screens are implemented.

The design system should support the product, not become a separate project.

⸻

41. Design Definition of Done

A screen is visually complete when:

* It follows the established hierarchy.
* Typography is consistent.
* Spacing is consistent.
* Interactive elements are clear.
* Loading states are considered.
* Error states are considered where relevant.
* Empty states are considered where relevant.
* Mobile behavior is intentional.
* Accessibility has been considered.
* The design feels consistent with the wider AquaCore product.
* No unnecessary decorative elements were introduced.

⸻

42. Final Design Principle

AquaCore should look like an organisation that knows what it is doing.

The interface should make customers feel:

“I understand what they offer, I trust the process, and I know what to do next.”

Professionalism should come from clarity, consistency, useful information, and strong execution rather than visual noise.
